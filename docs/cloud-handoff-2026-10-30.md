## 목적과 확정된 결정

haechi는 Claude Code와 Codex에 저장소 설정, 작업별 지침, 검증 도구를 제공하는 플러그인이다. 메인이 작업에 맞는 방법과 job을 선택하고 worker는 배정된 목표와 범위 안에서 방법을 고른다. 상시 규칙은 가볍게 유지한다. 파일 수, 고정 reviewer 수, 단계별 문서나 승인으로 작업을 통제하지 않는다. 이 구조는 제품의 설계이며, 실행 호스트가 위임을 제한하면 그 제한을 따른다.

원본은 루트 폴더에서 수정한다. `build/build.mjs`가 `dist/claude`와 `dist/codex`를 생성한다. 원본을 바꾸면 `npm run build` 후 `npm run check`로 생성본 일치를 확인한다. 생성본만 직접 고치지 않는다.

| 주제 | 유지할 결정과 이유 |
|---|---|
| 스펙 | 중요한 미결정 사항이나 명시적 요청이 있을 때 작성한다. 합의된 요구는 채팅에 남겨도 된다. 항상 스펙 파일부터 만드는 과거 방식은 복원하지 않는다. |
| 답변 | 내용에 맞는 문장·목록·표를 선택한다. 과거 A/B/C 고정 형식이나 별도 형식 설정을 복원하지 않는다. |
| 시안 | 빠르게 만드는 일회용 HTML과 가짜 데이터가 기본이다. 실제 앱이 필요한 판단은 실제 앱으로 확인한다. 저장소별 CSS 자동 생성과 디자인 토큰 연동은 유지 부담 때문에 채택하지 않았다. |
| 화면 검사 | 에이전트가 원본 이미지를 직접 열어 비교한다. 수치는 근거를 보조한다. 화면 보고서 생성만으로 실제 화면 검증을 주장하지 않는다. |
| 선택한 플레이북 | 명시적 사용자 선택만 세션과 작업 경로별로 기억한다. 단계 추적·편집 차단·자동 분류를 넣지 않는다. 실제 호스트의 명령 전달은 별도 검증한다. |
| 평가 | 실패 관찰과 원인 가설을 분리한다. 기준을 고정하고 새 맥락에서 반복 비교한 뒤 독립 판정한다. 한 번의 실패를 상시 규칙으로 기억시키지 않는다. |
| 백엔드 | v0.0.8의 프레임워크·migration·Docker 준비 기능은 v0.0.9에서 철회했다. 서비스 준비는 저장소가 소유하고 haechi는 검증 명령과 근거를 다룬다. |
| PR | 기존 `mr` 스킬이 GitHub PR도 처리한다. 별도 GitHub 본문 템플릿 추가는 필요가 커질 때까지 보류했다. |

시범 평가는 두 사례를 양쪽 각 2회, 총 8회 실행했고 모두 통과했다. 평가 체계 구현은 완료됐지만 행동 개선 효과는 입증하지 못했다. 이를 이유로 새 상시 규칙이나 자동 학습을 도입하지 않는다.

## 이번 Cloud에서 확인한 결과

- 환경 상태: `provider=cloud`, `running`, `connected`, 현재 관찰 결과 유효. Node.js `v24.19.0`.
- GitHub 연결 도구로 브랜치·커밋·PR 상태를 조회했다. 셸 기본 실행에서는 프록시 연결에 실패했지만, 이 실행 환경의 네트워크 권한을 포함한 명령으로 `git fetch`가 성공했다. 프록시 우회나 자격 증명 복사는 하지 않았다.
- 아래 테스트를 파일별로 실행했다. 기본 샌드박스 실행은 일부 파일에서 상세 원인 없는 파일 단위 실패만 보고했고, 필요한 실행 권한을 포함한 재실행 결과는 다음과 같다. 환경 차이의 원인을 코드 결함으로 단정하지 않는다.

| 명령 | 직접 관찰한 결과 |
|---|---|
| `npm run check` | 생성본 133개 일치 |
| `node --test --test-reporter=tap test/build.test.mjs` | 11 통과 |
| `node --test --test-reporter=tap test/rules.test.mjs` | 11 통과 |
| `node --test --test-reporter=tap test/skill-context.test.mjs` | 4 통과 |

제외된 평가는 Windows 파일명 대소문자 별칭 사례다. Linux에서 실행할 수 없는 플랫폼 검사이며 통과로 세지 않았다. 전체 테스트 명령은 실행하지 않았다.

인계 문서의 상대 링크를 확인했다. 이후 사용자의 정리에 따라 대화 전문 보관 파일은 제거하고 작업용 요약만 유지한다.

생성된 `dist/codex/hooks/inject.mjs`를 별도 임시 상태 폴더에서 실행해 `SessionStart` JSON 출력에 실제 저장소의 verify 명령과 금지 명령이 포함되는 것을 확인했다. 생성된 `check-settings.mjs`도 현재 `.haechi.json`을 complete로 판정했다. 임시 상태 폴더는 제거했다. 이는 훅 코드의 Cloud 실행 증거이며, 현재 채팅 호스트의 자동 훅 호출 증거는 아니다.

`codex --version`은 `0.163.0`이었다. `codex plugin list`는 원격 카탈로그 연결 실패 후 플러그인 없음으로 출력했다. 따라서 설치 여부와 자동 호출은 확정할 수 없다. 이 작업에서 플러그인을 설치하거나 훅 신뢰 승인을 변경하지 않았다. 개발과 인계에 필요한 명령·읽을 문서는 `AGENTS.md`에도 남겨 자동 훅 호출에 의존하지 않게 했다.

## 남은 일과 다음 작업

1. **공유된 인계에서 이어간다.** 사용자의 릴리즈 요청에 따라 인계 요약을 `codex/release-0.0.12`에 포함한다. 대화 전문을 추가했다가 제거한 로컬 커밋은 릴리즈 브랜치 이력에 포함하지 않는다. 게시 후 새 Cloud 작업에서는 `v0.0.12` 또는 해당 커밋을 포함한 main을 선택하고, 이 문서의 남은 일부터 이어간다. 같은 Cloud 채팅도 계속 이어서 열 수 있다.
2. **호스트에서 haechi 활성화를 검증한다.** 저장소 체크아웃과 플러그인 설치는 별개다. 현재 호스트가 지원하는 설치 경로와 훅 이벤트 전달을 확인한 뒤, 명시적 플레이북 선택·후속 입력·압축 후 복원·다른 세션과의 격리를 실제 호스트에서 확인한다. payload 테스트만으로 완료라고 하지 않는다.
3. **훅 신뢰 판정 문제를 재현한다.** `tools/check-user.mjs`는 `trusted_hash` 존재만 확인한다. 업데이트나 경로 변경 전후의 실제 신뢰 의미를 확인하고 실패 재현 후 수정한다.
4. **평가는 실제 실패로 이어간다.** 원문 실행 기록과 인접 정상 사례를 확보하고 기준을 고정한다. 시범 평가를 행동 개선의 증거로 재사용하지 않는다.
5. **실환경 검증을 구분한다.** 실제 디자인 시안·앱/Figma 화면 비교·GitLab CI 실행은 이번 작업에서 검증하지 않았다. Windows 단일 인용 경로 지원도 미결정이다. 과거 Windows 테스트 20 통과·2 제외는 과거 보고이며 이번 Linux 결과와 합치지 않는다.

과거 인계의 커밋 신원 미결정 항목은 이후 `haechi 설정` 채팅에서 사용자 계정 `jisuzzzz`로 정정됐다는 보고가 있다. 현재 Cloud의 전역 작성자는 다른 신원이므로 그대로 사용하지 않는다. 이번 후속 커밋에는 기존 `c5c7ed8`의 `jisuzzzz`와 GitHub noreply 이메일을 명령별로 지정한다. Git 인증 계정과 커밋 작성자는 별개이며, 과거 커밋이나 태그는 다시 쓰지 않는다.

비공개 단어 검사에 필요한 패턴은 이번 환경에 구성됐다는 증거가 없어 `npm run scan`은 실행하지 않았다. CI는 기존에 Node 22와 `npm test`를 사용한다. 이번 인계는 Cloud Node 24에서 파일별 검증만 했으며 CI 설정은 변경하지 않았다.
