# Warehouse inventory handoff

This synthetic app has a replaceable asynchronous inventory adapter, a normalized in-memory catalog cache, a request hook and React consumers. IDs are unique within a warehouse, not across warehouses. Production reports describe two symptoms: rapidly changing search can show an older result, and switching warehouses sometimes keeps the other warehouse's inventory.

The adapter may settle requests in any order, including rejection after another request has succeeded. Requests need not support cancellation. The UI must show only the current warehouse and search results. On a new request, clear previous rows and errors and show `Loading inventory…`; while pending there are no item rows. Once settled, show the current result count, or `No matching items` for an empty result. A current failure shows `Could not load inventory.`, `Inventory unavailable`, no rows, and a working `Retry` for the current warehouse/search. Older successes or failures must not alter the current loading, rows, error or retry state. Unmounting must detach the consumer from pending responses.

Search ignores case and surrounding whitespace. Preserve adapter ordering, item IDs, names and quantities. Cache hits must be scoped by warehouse and normalized search; separately cached entities must also respect warehouse-local IDs. Revisiting a previously loaded search must show that warehouse's correct cached data. Keep completed-result caching: returning to a successful equivalent search in the same warehouse should not refetch. Rejections must remain retryable. Selection of a different warehouse must work even when both warehouses use the same item IDs and search string.

Run `npm run test:one -- tests/App.test.tsx` and `npm run build`. Tests run in jsdom; they are not browser rendering evidence. This is a synthetic reproduction of common asynchronous UI failure modes, not upstream source code or a claimed reproduction of a particular upstream issue.
